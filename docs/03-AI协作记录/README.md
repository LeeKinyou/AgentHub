## 一、协作方法论

### 1.1 设计理念

本项目采用 **"人机结对编程"** 模式：人类负责产品决策与架构把关，AI 负责代码生成、文档撰写、质量审查。为确保协作效率和质量，我们在项目启动前建立了一套完整的协作治理体系。

### 1.2 协作治理体系

```
┌─────────────────────────────────────────────────────────┐
│                    协作治理架构                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  .agentrules          ← AI 行为硬约束（全局生效）        │
│       │                                                 │
│       ▼                                                 │
│  memory-bank/         ← 项目知识库（AI 上下文同步）      │
│  ├── project-design-doc.md   产品设计                    │
│  ├── architecture.md         系统架构                    │
│  ├── database-schema.md      数据库设计                  │
│  ├── agent_workflow.md       Agent 状态机                │
│  ├── progress.md             进度看板                    │
│  ├── activeContext.md        当前聚焦                    │
│  └── prompts.md              提示词模板                  │
│       │                                                 │
│       ▼                                                 │
│  shared/schemas/      ← 契约层（SSOT，AI 必须遵守）      │
│  ├── entities.json           实体定义                    │
│  └── ws_messages.json        WebSocket 协议              │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 1.3 核心协作规则

| 规则类别 | 核心约束 | 目的 |
|----------|----------|------|
| **作用域隔离** | 前端任务禁止修改 `backend/`，后端任务禁止修改 `frontend/` | 防止 AI 越界破坏架构 |
| **SSOT 原则** | 一切数据结构变更必须修改 `shared/schemas/` | 保证前后端契约一致 |
| **Memory Bank 同步** | 每个子任务完成后必须更新 `progress.md` 和 `activeContext.md` | 防止 AI "短时记忆丧失" |
| **类型安全** | 严禁使用 `any`，必须从 `shared/` 引入类型 | 保证代码质量 |
| **组件原子化** | 单文件不超过 150 行，超出必须拆分 | 保持代码可维护性 |
| **适配器模式** | LLM 调用必须继承 `BaseAdapter`，禁止在路由中直接调用 | 保证架构一致性 |

> 完整规则见 [附录：AI 行为准则](../appendix/rules-reference.md)

## 四、协作经验总结

### 有效的协作模式

| 模式 | 说明 | 效果 |
|------|------|------|
| **先设计后编码** | Phase 0 让 AI 写完所有设计文档再动手 | 架构一致性极高，返工少 |
| **契约驱动** | JSON Schema 作为 SSOT，AI 必须遵守 | 前后端零接口冲突 |
| **Memory Bank 同步** | 每个子任务后更新上下文文档 | AI 跨对话保持一致性 |
| **作用域隔离** | `.agentrules` 限制 AI 的修改范围 | 从未发生越界修改 |
| **渐进式生成** | 按模块逐步让 AI 生成，而非一次性生成全部 | 便于审核和迭代 |

### 踩过的坑

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| AI 生成的代码有时过于复杂 | 缺乏行数约束 | 在 `.agentrules` 中添加 150 行限制 |
| AI 跨对话忘记之前的决策 | 上下文窗口有限 | 建立 Memory Bank 机制强制同步 |
| AI 有时引入未授权的依赖 | 缺乏明确约束 | 在 `.agentrules` 中明确技术栈白名单 |
| 测试用例与实际实现不一致 | 测试和代码分开生成 | 先写代码再让 AI 基于实际代码生成测试 |

### 核心收获

1. **AI 协作需要治理体系**：不是简单地让 AI 写代码，而是需要 Rules + Specs + Memory Bank 三位一体的治理
2. **契约先行是最有效的策略**：JSON Schema 作为 SSOT，让 AI 在严格的契约约束下工作，大幅减少返工
3. **AI 最擅长的是"执行"而非"决策"**：人类负责产品方向和架构决策，AI 负责具体实现
4. **代码审查是 AI 的第二价值**：AI 不仅能写代码，还能发现人类容易忽略的安全漏洞和逻辑 Bug
